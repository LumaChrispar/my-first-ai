# Aster Small Model: Detailed Build Specification

**Document purpose:** hand this file to a coding AI as the implementation brief for the first real, trainable Aster model and its local chat interface.

**Project status:** design brief; Aster currently has a C rule-based demo server and a browser UI. The rule-based reply code is temporary and must not be presented as a language model.

**Date of model landscape notes:** 2026-09-30. Model names, access, prices, capabilities, and safety measures change quickly. Re-check the linked official pages before making new comparisons.

---

## 1. Implementation mission

Build a small, educational, text-only language model implemented in C that can be trained from local text files and used through Aster's existing local browser chat interface. The first version should be small enough to inspect and run on an ordinary desktop CPU. It must be honest about how limited it is.

This is a foundation for learning and future experimentation. It is **not** a frontier model, an AGI, an SGI, a reliable general-purpose assistant, or evidence that either of those outcomes is near. No implementation plan can promise those outcomes.

The first successful result is concrete and modest:

1. A C program reads a prepared local dataset.
2. It turns bytes/text into token IDs.
3. It trains a tiny causal transformer to predict the next token.
4. It writes a versioned model checkpoint to disk.
5. It can load that checkpoint and generate a short continuation.
6. The local web UI sends a chat prompt to the C program and shows the generated output, errors, and model status accurately.

The project should optimize for **understandability, reproducibility, privacy, and truthful presentation**, not for claiming to beat large commercial models. Aster can be better in these narrow ways: its code and small-model behavior can be inspectable; training can be repeated locally; prompts and model weights need not leave the computer; and limitations can be shown directly in the interface. These properties do not make its answers more capable or more accurate.

## 2. Instructions to the implementation AI

Work in the existing project folder. Inspect the current files first. Preserve and improve the existing dark, responsive chat UI where reasonable. Replace the current hard-coded rule replies with the actual model path. Do not silently leave the rules in place and label the result “AI.”

Implement the smallest complete end-to-end path before adding optional features. Use portable C11 for the model/trainer and a small local HTTP server. Do not add a cloud API, API key, external model download, telemetry, automatic web search, tools, or remote data transfer. Do not invent a pre-trained Aster checkpoint. If no checkpoint exists, the UI must explain how to train one and the server must report “model not trained” rather than returning random text as if it were a useful answer.

Make routine engineering decisions without asking the project owner questions. If a dependency or hardware feature is optional, keep the default path CPU-only and dependency-light. Document any limitation caused by the local computer or compiler.

## 3. What the first model is and how it behaves

### 3.1 Model type

Use a **decoder-only causal transformer**. It receives a sequence of token IDs and predicts a probability distribution for the next token. Generation repeatedly selects a token from that distribution and appends it to the context. It has no separate fact database and no mechanism for checking whether a plausible sentence is true.

For the first version, use a **byte tokenizer** to avoid downloading a tokenizer or relying on third-party code:

- Token IDs `0` through `255` represent the corresponding byte values. Ordinary UTF-8 text is encoded as its UTF-8 bytes.
- Reserve IDs `256` through `259` for `SYSTEM`, `USER`, `ASSISTANT`, and `END` conversation markers.
- If a padding ID is needed for batching, reserve `260` and ensure padding positions do not contribute to the loss.
- Store the tokenizer/version identifier in every model checkpoint. Changing token meanings requires a new checkpoint version.
- On output, validate generated byte sequences as UTF-8. Replace invalid sequences safely for display; never let malformed output crash the server or UI.

This tokenization is deliberately simple, but inefficient: a word may take several bytes and non-English text can take many. The 128-token model context below is therefore often much shorter than 128 words. A later version may add a tested BPE tokenizer, but that is not part of the first milestone.

### 3.2 Initial model size and settings

Use these small, named defaults, and allow them to be changed only through explicit configuration:

| Setting | Initial value | Reason |
|---|---:|---|
| Transformer blocks | 2 | Keeps the network small enough to inspect and train as a learning exercise. |
| Hidden width (`d_model`) | 64 | Small CPU-oriented representation size. |
| Attention heads | 4 | Each head has width 16; require `d_model % heads == 0`. |
| Feed-forward width | 256 | Four times `d_model`, a conventional simple baseline. |
| Context length | 128 tokens/bytes | Bounds memory and attention work; this is short. |
| Vocabulary | 261 IDs including reserved markers | Fixed byte vocabulary and control markers. |
| Precision | 32-bit float | Easiest first implementation to understand and debug. |
| Optimizer | AdamW or Adam with documented weight decay | Standard, understandable baseline. |
| Generation default | 80 new tokens maximum | Keeps early generations short and UI responsive. |

This is roughly a **0.13-million-parameter educational network**, depending on biases and whether input/output embeddings are tied. Print the exact parameter count at startup. Do not call it a “small frontier model”; it is several orders of magnitude smaller and trained on far less data than contemporary frontier systems.

Use learned token and positional embeddings, pre-layer normalization, masked causal self-attention, residual connections, a GELU feed-forward block, a final layer normalization, and a linear output head. Weight tying between token embeddings and the output head is recommended to reduce the parameter count, but must be implemented consistently in both the forward and backward passes.

### 3.3 User-facing behavior

The first trained checkpoint should behave like a **short, experimental text generator**, not like a competent all-purpose assistant. Depending on the training data and fine-tuning, it may:

- continue a short prompt in a style resembling its training examples;
- learn frequent word and character patterns;
- sometimes produce a recognizable answer if similar question/answer examples were included;
- repeat itself, contradict itself, switch topics, emit fragments, or produce invalid-looking claims;
- fail at arithmetic, exact facts, long instructions, unfamiliar topics, non-English text, and multi-step reasoning.

The model has no web access, image/audio/video input, tools, autonomous actions, reliable persistent memory, source citations, or independent fact checking. It cannot inspect the user's computer files beyond input explicitly sent to the local application. It must never claim it searched, opened a file, remembered a past session, checked a fact, ran code, or completed an action unless a later, explicit feature actually did so.

The chat UI may retain a conversation in the current browser tab or local browser storage if this is clearly documented and there is a visible **Clear chat** action. The C server must not save message history by default. The model's context is a temporary prompt assembled for each request; it is not human-like memory or learning from the conversation.

### 3.4 Reply style and uncertainty

The UI should identify Aster as an experimental local model. Show at least:

- whether the model checkpoint is loaded;
- the model/checkpoint name and configuration when available;
- a warning that answers can be fluent but wrong;
- a concise notice that it does not browse the internet or use external tools;
- an error state if training is needed, a request is too long, the server is offline, or generation fails.

Do not hard-code universal claims like “I understand everything,” “I am accurate,” or “I am learning from you.” If the model is uncertain, the text model may not reliably express that uncertainty. The product should not turn a low token probability into a guarantee of factual confidence. If there is no checkpoint or a request cannot be handled, report the operational reason outside the generated answer.

## 4. Training data: what it needs

### 4.1 Data source and rights

The trainer should accept user-provided local plain-text files and a small, clearly identified, project-authored demonstration corpus if one is needed for a runnable example. Do not scrape the internet, copy a commercial model's outputs wholesale, bundle books or datasets without checking their license, or claim a tiny sample has broad coverage.

For each dataset, document provenance, license/permission, collection date if known, processing steps, and a cryptographic hash. Keep a manifest alongside the data. Exclude private conversations, credentials, API keys, personal records, and confidential work unless the owner explicitly has the rights and a deliberate privacy process. Deduplicate exact repeated text and remove corrupt/empty files. Preserve line breaks where they matter.

The dataset's volume is not a promise of quality. A small corpus can teach format and local patterns; it cannot provide broad world knowledge. The training program should print which files it read, how many bytes/tokens/examples survived cleaning, and which manifest it used.

### 4.2 Data formats

Support two clear modes:

1. **Pretraining text mode:** UTF-8 `.txt` files. Concatenate files with explicit document-boundary/end markers so the model is not trained as if unrelated file endings and beginnings were one sentence.
2. **Instruction-tuning mode:** a simple documented UTF-8 line format or JSONL with role/content messages. Require well-formed `system`, `user`, and `assistant` turns. Mask the loss on system/user prompt tokens if the chosen objective is to train only assistant responses. Do not silently parse malformed examples as valid conversations.

Create training, validation, and test splits by document or source before chunking. Do not put near-duplicate passages from the same source on both sides of a split. Report each split size. The held-out test set must not be used for gradient updates, hyperparameter search, or prompt-writing.

### 4.3 Training objective and procedure

Train with next-token cross-entropy. At each position, give the model only the preceding context and compare its next-token distribution with the actual next token. Apply a causal mask so no position can see future tokens. For instruction examples, follow the documented loss mask.

Provide a seeded, repeatable shuffle and initialization. Log the seed, configuration, dataset hashes, step, elapsed time, training loss, validation loss, and tokens/second. Allow a user to stop training cleanly. Save checkpoints to a temporary file and rename on success so interruption does not corrupt the last good checkpoint. If implementing resume, persist optimizer state and step count as well as model parameters.

Include a documented learning rate, warmup or simple schedule, batch size, gradient clipping, and weight decay. The first implementation should favor a correct, understandable CPU trainer over premature optimization. If full backpropagation through this transformer is too large for one implementation pass, reduce the configured model or sequence/batch size; do not fake training by writing random weights or hard-coding canned replies.

## 5. C implementation requirements

### 5.1 Code structure

Keep modules small and interfaces explicit. A reasonable layout is:

```text
src/
  main.c          command-line dispatch and startup
  tokenizer.c/.h  UTF-8 byte encoding and special markers
  model.c/.h      configuration, parameters, forward pass, generation
  train.c/.h      dataset batching, loss, gradients, optimizer, checkpoints
  server.c/.h     localhost HTTP routes and request parsing
  util.c/.h       checked allocation, logging, paths, seeded RNG
data/
  README.md       data rights/provenance instructions and formats
models/           generated model files; not committed unless intentionally included
index.html         browser interface
README.md          build, data preparation, train, run, and limitation guide
```

The implementer may adjust names, but training, inference, tokenizer, and HTTP responsibilities should not be tangled into one giant function. Use checked size calculations before allocating tensors. Handle allocation failure with a clear error and cleanup. Avoid variable-length stack arrays sized from user input.

### 5.2 Numerics and transformer correctness

Implement and document the following carefully:

- numerically stable softmax: subtract the maximum logit before exponentiation;
- a strictly causal attention mask;
- correct attention scaling by the square root of the head dimension;
- layer normalization with epsilon;
- residual additions and gradient flow;
- stable cross-entropy using log-sum-exp or an equivalently stable calculation;
- gradient clipping before optimizer update;
- deterministic random number generation when a seed is provided;
- bounds checks for token IDs, sequence lengths, tensor dimensions, and checkpoint values.

Use a clear tensor layout and document dimension order in headers. A tiny implementation can use plain loops. Optimize only after correctness and profiling; first avoid undefined behavior, integer overflow, uninitialized memory, and silent NaNs.

### 5.3 Checkpoint format

Define a binary checkpoint format with:

- magic bytes and format version;
- tokenizer and architecture version;
- model hyperparameters and exact parameter count;
- training step and seed where applicable;
- optional data/config metadata or a sidecar manifest;
- serialized weights (and optimizer state if resumable);
- validation of all lengths before allocation or reading.

Reject an incompatible, truncated, corrupt, or unsupported checkpoint with a useful error. Never interpret arbitrary files as model weights. Do not put chat logs or user prompts in the checkpoint.

### 5.4 Command-line interface

Provide discoverable help, nonzero exit codes on failures, and at least commands equivalent to:

```text
aster --help
aster train --data data/train.txt --validation data/validation.txt --out models/aster-small.bin --seed 1234
aster generate --model models/aster-small.bin --prompt "Once upon a time" --max-new-tokens 80
aster serve --model models/aster-small.bin --host 127.0.0.1 --port 8080
```

Names/options can differ if the README documents them and the same three actions are available. The web server must bind to loopback by default. Do not bind to all network interfaces unless a separate, explicit opt-in feature is implemented with appropriate security controls.

The build should support the project owner's Windows setup with MinGW-w64 GCC or a documented Visual Studio path. Prefer C11 and no third-party dependency for the CPU baseline. If a POSIX path is straightforward, keep socket code behind a small platform layer; Windows is the primary target. Include exact PowerShell build/run commands in the README. Do not assume `gcc` exists: explain how to check the compiler and report the error clearly.

### 5.5 HTTP and browser interface

Retain a simple local browser chat, but replace brittle one-shot request parsing with bounded, length-aware HTTP handling. Set a maximum request/body size; check content length; reject malformed JSON and oversized input; escape JSON output correctly; send UTF-8 headers; close each connection safely. The initial user-facing route may preserve compatibility with the existing `POST /api/chat` `{ "message": "..." }` shape. Add a health/status route that states whether a compatible model is loaded.

The server should return a clear service-unavailable response when no model is loaded, invalid input errors as client errors, and model/runtime errors without exposing stack traces or private local paths. Do not reflect untrusted input into HTML. The UI must render user and model messages as text, not executable HTML.

Keep the interface useful on mobile and desktop. Include send, loading state, visible generation failure, clear-chat, and a short local prototype warning. A Stop button is desirable if generation is cancellable. Never show a fake “thinking” indicator as evidence of hidden reasoning. If the model produces raw text, display raw text plainly.

## 6. Sampling and inference

Implement greedy generation first, then temperature and top-k as explicit optional settings. Defaults should be conservative and deterministic with a seed for repeatable debugging. Validate `temperature > 0`, cap top-k to vocabulary size, enforce `max_new_tokens`, stop on the end marker, and guard against an empty candidate distribution or non-finite logits. Do not include hidden chain-of-thought display or claim that generated internal text is verified reasoning.

Before inference, fit the prompt to the context. Preserve the fixed system marker and the most recent complete user/assistant turns if dialogue format is supported. If truncation is required, indicate that older context was dropped; do not silently pretend the entire history fit. With a 128-byte context, a prompt plus answer can be very short.

The inference program must load the same tokenizer and architecture version used by training. It must not silently switch models or fetch weights from the network.

## 7. Safety, privacy, and appropriate use

This first version has no action tools. Keep it that way. A text generator should not be able to run shell commands, browse files, send email, install packages, spend money, or contact external services. Do not add a “tool” endpoint that forwards model-created commands to the operating system.

Treat model output as untrusted text. A tiny model is not made reliably safe just by adding a safety sentence to a prompt or a handful of refusal examples. It may ignore such instructions, confidently generate incorrect information, or reproduce training text. Do not present it for medical, legal, financial, emergency, hiring, or other high-impact decisions. Do not claim safety certification.

Keep all traffic on `127.0.0.1`, make network use absent by default, and do not log prompts by default. Explain any browser local-storage behavior and make clearing it easy. The code should never print dataset contents or user prompts in normal logs. Provide a data manifest mechanism and warn the owner not to put secrets or private personal records into the training corpus.

## 8. Evaluation and definition of done

An implementation is not complete just because it compiles or produces text. It must have a small, documented validation plan that another person can repeat.

### Required evidence

1. **Build:** exact clean-build command succeeds on the documented Windows compiler path. If compiler availability blocks this, document the missing prerequisite rather than claiming success.
2. **Tokenizer:** round-trip ordinary ASCII and valid UTF-8 through encode/decode. Special tokens remain distinct; unknown/bad input does not overrun buffers.
3. **Training:** using a tiny project-authored sample corpus, the program takes several updates, reports finite training/validation losses, and writes a checkpoint. Do not require the validation loss to fall on every individual step; stochastic batches fluctuate.
4. **Learning signal:** over a documented short run, the model's held-out loss should be meaningfully below its initial/untrained loss on the same fixed validation set. If not, report the issue; do not fabricate improvement.
5. **Reload:** the program reloads the written checkpoint and can generate a bounded continuation. Same prompt, checkpoint, seed, and settings reproduce the same result in deterministic mode.
6. **Failure cases:** malformed checkpoint, missing checkpoint, too-long request, invalid JSON, empty prompt, and allocation failure return controlled errors rather than crashing.
7. **Server/UI:** health status agrees with the loaded checkpoint; chat displays a model response or the precise operational error; browser cannot inject message text as HTML; server listens only on loopback by default.
8. **Honesty:** interface, help text, and README explicitly call this a tiny experimental model and describe the absence of reliable knowledge, tools, web access, and long memory.

Do not report “good at everything” based on a few examples. Record evaluation corpus, seed, model hash, tokenization, settings, and command. Compare Aster versions on the **same** local evaluation set before claiming improvement. Commercial benchmark figures from separate labs are not a substitute for this test.

## 9. Comparison with current model families: lessons, not a scoreboard

The competitive landscape is much larger than can be exhaustively listed, and new versions appear frequently. This section uses the likely intended names from the project owner's request: **GPT-6 Astra** and **Claude Fable** (“feble” is interpreted as “Fable”). It also notes Google's Gemini and Project Astra because the names are easy to confuse. If “feble” meant a different model, update this section rather than guessing.

Specifications and capabilities below are published by their makers and are not independent proof that every output is correct. Context-window size means how much input a system may accept; it does not guarantee that the system will accurately use every item in that context. Tool and multimodal capabilities are often properties of an entire product stack—model, APIs, retrieval, orchestration, safeguards, and interface—not just neural weights.

### GPT-6 Astra (OpenAI)

OpenAI describes GPT-6 Astra as a high-end model for demanding reasoning, coding, computer use, research, and document work; its API page lists a context window of about 1.05 million tokens and up to 128,000 output tokens. OpenAI's published Astra material also discusses cyber capability and deployment safeguards, which is a reminder that stronger capability can increase misuse risk as well as useful defensive capability.

**Design lessons for Aster:** say exactly which engine is running; separate the model from UI/tool integrations; test task boundaries and unsafe behavior; require explicit permission and restricted execution before ever adding tools; track model/checkpoint versions. **What Aster does not inherit:** Astra's scale, data, training compute, research, long context, multimodal perception, computer-use stack, or production safety infrastructure. A 128-token Aster model cannot be fairly described as competing with Astra.

### Claude Fable 5.1 (Anthropic)

Anthropic describes Claude Fable 5.1 as aimed at demanding reasoning and long-running agentic coding/research and document, spreadsheet, and slide work. Its published API documentation lists a one-million-token context, up to 128,000 output tokens, adaptive thinking, and slower comparative latency than Anthropic's faster model tiers. These details are version-specific and may change.

**Design lessons for Aster:** performance involves trade-offs such as latency, output budget, and task difficulty; evaluate the workload that matters instead of assuming one “best” model fits every use. Aster's first version should instead be small, local, and inspectable. **Limitation of comparison:** Fable's system, training data, and full implementation are not reproduced by a small public-facing C project; a large context number alone would not make Aster more capable.

### Gemini and Project Astra (Google)

Google's current Gemini family spans different model sizes and task targets; its public material describes multimodal input and long-horizon or tool-supported work for selected models. Google's Project Astra is a research/product effort toward an interactive, multimodal assistant, including audio/video or visual context, memory, and tools in some experiences. It is not the same thing as the OpenAI model named GPT-6 Astra.

Google's Gemini model cards explicitly list general foundation-model limitations such as hallucinations for some versions, discuss jailbreak resistance as ongoing work, and note possible slowness/timeouts. Google's long-context guidance also cautions that performance varies by context and by how many details must be retrieved. These are practical examples of why a long input window or impressive demo is not a guarantee of dependable answers.

**Design lessons for Aster:** keep text-only scope explicit; do not label the app multimodal until it actually receives and processes images/audio/video; don't call local browser storage “intelligent memory”; and make availability/runtime errors visible. Adding voice, vision, retrieval, or actions later requires separate data, models, permission boundaries, and evaluations.

### Open-weight and smaller model families

Open-weight models can be downloaded, inspected to varying degrees, fine-tuned, and run locally, subject to each model's license, hardware requirements, and model-card limits. They provide useful future comparison and learning options. “Open weights” does not necessarily mean the complete training data, recipe, or commercial usage rights are open. Aster's from-scratch byte-level model is more educational and easier to inspect, but is expected to be far less useful than a well-trained open model of billions of parameters.

### The comparison Aster should actually make

Do not claim that Aster is “better than GPT/Gemini/Claude” in general. Measure and report narrow dimensions such as:

- runs offline after the owner supplies data and trains it;
- no per-token API bill;
- prompt is not sent to a model provider by this application;
- exact model size, training corpus, tokenizer, and configuration are visible;
- reproducible output under a fixed checkpoint and seed;
- token loss on a clearly described local held-out dataset;
- speed and memory use on the owner's actual computer.

Those would be concrete distinctions, not proof of superior intelligence, factuality, safety, or general usefulness.

## 10. Growth path after the first model

Treat future capabilities as separate milestones. Do not combine them into the initial implementation.

1. **Small text model (now):** correct tokenizer, transformer, training, inference, checkpointing, local UI, honest limitations.
2. **Better text quality:** improve licensed data curation, tokenization, training stability, instruction examples, and held-out evaluation; increase model size only when compute and memory are measured.
3. **Retrieval:** add explicit local document indexing and citations. The system should distinguish retrieved passages from model-generated text and show sources. Retrieval is not a substitute for correct reasoning.
4. **Evaluation-led specialization:** choose a named task (for example, answering questions about a user's own project notes) and optimize it with separate test data. Avoid “everything” claims.
5. **Tools/actions:** only after capability and threat evaluation. Each tool should have narrow permissions, input/output validation, audit logs, a sandbox when relevant, and user confirmation for consequential actions. Model text alone never authorizes an action.
6. **Multimodal input/output:** separate image/audio/video encoders or specialist models, licensed datasets, accessibility evaluation, and privacy controls.
7. **Larger-scale research:** scaling to frontier capability would require far greater compute, high-quality large-scale datasets, distributed training, specialist hardware/software, extensive evaluation, safety research, and a team. C can remain useful for inference/runtime and learning; a pure-C CPU project is not a credible way to train a frontier model on a personal desktop.

AGI or superintelligence should remain an open research aspiration, not a milestone claim. Define concrete task capabilities and pass credible evaluations before describing what the system can do.

## 11. Deliverables and final handoff expected from the implementation AI

Produce:

- the working source code and local browser UI;
- a documented training data format and provenance/license manifest template;
- a small, clearly labeled original demonstration corpus only if needed for first-run training;
- build, train, generate, and serve instructions for Windows PowerShell;
- exact model configuration, parameter count, checkpoint version, and memory limitations;
- a concise model card recording intended uses, non-uses, training data, evaluation results, and known failures;
- a short implementation summary stating what was actually built and which commands were actually run.

Do not claim a test, compiler build, training run, benchmark, or browser launch succeeded unless it was actually performed. If anything could not be run on the available machine, name the blocker and give the owner the exact command to run.
